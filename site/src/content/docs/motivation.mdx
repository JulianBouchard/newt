I started newt while building customer-facing agents for a product. The same problems kept coming up, and none of the runtimes I tried really cared about them.

## Every framework wants its own agent

Every agent framework and hosted runtime has its own way to define an agent. Its own tool format, its own way to handle prompts and state, its own idea of where context comes from. Moving an agent to another runtime means rewriting it, and you can't really try one without committing to it first.

MCP already describes the parts of an agent, instructions, tools, resources and skills, and no vendor owns it. So in newt the agent is just an MCP server, written with any MCP SDK, and newt runs it. Want to try another runtime? Point it at the same server. Want to test the agent? Open it in any MCP client.

## A product is one API, not three

Putting an agent into a product today usually means building the same thing several times. The backend API, the frontend, an MCP server for other people's agents, and the agent itself. They get built separately and drift apart. The UI shows a field the agent can't read, or the agent changes something the UI never notices.

They should be one thing, **one core API that does the work**, opened up in three tiers depending on who's calling.

| Tier | Who calls it |
|---|---|
| **Public** | Anyone browsing |
| **Authenticated** | A logged-in user, acting on their own data |
| **Private** | A logged-in admin, or your own backend |

Each tier is wrapped twice, as routes for your frontend and as an MCP server for agents. The public and authenticated MCP servers are for other people's agents, and the authenticated one acts as the logged-in user, just like the frontend does. The private MCP server has the internal context and operations only your own agent should have, and it's that agent's [core](../agent-core/).

Your frontend already has these tiers. An agent is just one more client of the same API, at whatever tier it's allowed.

## One way to say what changed

Frontends solved stale data with query keys. A mutation says which keys it changed, and React Query refetches those queries in the background. newt's pages work the same way. Every page has a key, and a tool says which keys it changed.

Put the two together:

1. A person clicks in the UI, so the frontend calls a route. Or the agent calls a tool.
2. Both reach the same API, which does the work and returns the keys it changed: `invalidate ['tasks']`.
3. The UI refetches the tasks in the background. The agent's `tasks.md` page goes stale, so its next read gets the new list.

The UI and the agent always read the same data, and it stays current the same way for both. That's what I want agentic UI to mean. The app and the agent are two clients of one API, not a chat box bolted onto the side.
