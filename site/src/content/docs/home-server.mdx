An agent is one MCP server, its home, plus any [servers it adds](../servers/). Build the server with any MCP SDK and the agent comes with it. newt has no other interface for your app to implement.

```toml
[agents.assistant]
mcp = "https://app.example.com/mcp"
token_env = "ASSISTANT_TOKEN"
```

One token authenticates both directions: callers send it to newt as `Authorization: Bearer`, and newt sends it to a home reached over HTTP.

## Hosted, bundled or run by newt

The same server code runs three ways, like newt's own database:

| `mcp =` | Who runs the server |
|---|---|
| `"https://agent.example.com/mcp"` | Someone else, as its own deploy. |
| `"http://localhost:4000/mcp"` | You, next to newt in the same deploy. |
| `"stdio:node ./agent/server.js"` | newt. It starts the command, speaks MCP over its stdin and stdout, and starts it again if it exits. No network, no token. |

Switching between them is this one line. You can also open the server in MCP Inspector or Claude Code to test it without newt.

## What newt takes from the home

| The agent's | Comes from |
|---|---|
| System prompt | The server's `instructions`. Empty instructions fail the turn. |
| Model and settings | The `newt` extension it declares on `server/discover` |
| Tools | `tools/list` |
| Skills | [`skills/list`](../skills/), named `{agent}/{skill path}` |
| Workspace pages | Its resources, listed and read per session |
| Per-turn guidance | `newt/turn`, if it declares `turn: true` |
| After each turn | `newt/turn_end`, if it declares `turn_end: true` |

## Declare the agent

The home declares the agent's settings in its capabilities, as the `newt` extension:

```json title="server/discover result"
{
  "instructions": "You are a personal assistant for one person, reached by chat.",
  "capabilities": {
    "tools": {}, "resources": { "subscribe": true },
    "extensions": {
      "newt": { "model": "default", "effort": "medium", "turn": true, "turn_end": true }
    }
  }
}
```

`model` is a `[models]` alias from `server.toml`: the home picks the alias, `server.toml` decides which providers it means. Optional knobs (`max_model_calls`, `history_budget`, `servers` and more) are in [Protocol 1.2](../protocol/#12-the-newt-extension-the-agents-settings). Unknown fields fail the turn loudly.

The instructions, skills and tools form the cached prompt prefix. Change them and the next turn pays one prompt cache miss. newt reads the declaration again whenever it reconnects, which includes the server restarting or announcing a tool change.

## Resources are the workspace

newt lists and reads the session's resources at the start of each turn, in the background, with `_meta: { "newt/session": "<key>", "newt/state": … }`, so one server can serve every session. The first `read_file`, `glob` or `grep` waits for them. Each text resource becomes a page:

| Page field | From the resource |
|---|---|
| `path` | `name` |
| `key` | `_meta["newt/key"]` when set, otherwise `[uri]`. Tools mark pages stale by key prefix. |
| `version` | The `sha256:` digest of the text. newt tells tools which version the agent read. |
| `content` | The text contents |

Pages are rebuilt from your app, never edited by newt. newt subscribes to the session's resources for the rest of the turn: `notifications/resources/updated` marks one page stale and `notifications/resources/list_changed` marks them all, and the next read fetches again. A tool can also mark pages stale or hand back fresh ones; see [Tools over MCP](../tools/#invalidation-works-like-react-query).

:::tip
The update notification travels on its own stream, so it can arrive after the tool result that caused it. A tool that changes a page should also return `newt/invalidate`, or the page itself in `newt/pages`, so the model's next read sees the change for certain.
:::

## This turn: `newt/turn`

Declare `"turn": true` and newt asks the home before each turn. It sends the events the turn answers and the state you returned last time:

```json title="newt/turn params"
{
  "session": "ana",
  "events": [{ "id": "m1", "meta": { "channel": "whatsapp" } }],
  "state": { "last_seen_task": 12 }
}
```

`events` lists each event's `id` and the `meta` your app posted with it, oldest first. Events that join the turn later as steering are not listed. `state` is `null` before the first turn.

You answer with this turn's guidance, every field optional:

```json title="newt/turn result"
{
  "pinned": "Write for WhatsApp: no markdown, two short paragraphs at most.",
  "instructions": "It is 2026-11-12T09:30:00Z.",
  "constraints": ["Do not message the person before Monday: they are on holiday."]
}
```

- `pinned` is session-stable text, such as the writing guide for the person's channel. It sits in the cached prefix.
- `instructions` and `constraints` reach the model at the start of this turn only and never enter history.
- `state` replaces the session state. See [Session state](#session-state).
- `turn_state` is the value the turn's tool calls start with, for facts only this request knows, such as the channel to reply on. See [Turn state](../tools/#turn-state).
- `model`, `effort`, `first_call_effort` and `reset` change how this one turn runs. See [Pick the model for one turn](#pick-the-model-for-one-turn).

A home that does not declare `turn` is never asked, and newt goes straight from the event to the model.

:::caution
Constraints are text the model reads. They do not block a tool call. Enforce any rule that must hold in your tool handlers too.
:::

## Pick the model for one turn

A `newt/turn` result can override the declared settings for this turn only:

```json title="newt/turn result"
{
  "model": "strong",
  "effort": "high",
  "first_call_effort": "medium"
}
```

- `model` is a `[models]` alias from `server.toml`. An alias that does not exist fails the turn before anything reaches the model, and the turn retries with backoff.
- `model`, `effort` and `first_call_effort` apply to every model call of this turn and to the compaction right after it. The next turn starts from the declared settings again.
- A different model is a prompt cache miss for this turn and for the next one on the usual model, so keep it for turns that are worth it.

### Start the conversation over

`"reset": true` runs the turn as if the session had no history. The model sees no earlier messages and no earlier checkpoint; the turn's events and its own messages start the new conversation. The session keeps its key, inbox, state and live feed. Use it when a conversation has gone cold, or when your prompt has moved on and the old history no longer fits it.

- Nothing is deleted. [History and fork](../replay/) still see every entry; they are only never loaded into the prompt again.
- The reset is saved by the statement that commits the turn. A turn that does not commit resets nothing, and its retry asks `newt/turn` again.
- Once a turn has journaled a model call, a resume after a crash keeps the model, efforts and reset it chose, whatever `newt/turn` answers the second time.

The live feed's `turn_started` frame carries the turn's `model` and `reset`.

## Session state

newt stores one JSON value per session for your agent and hands it back on every request, so the home needs no session store and any copy of it can answer. Use it for what the agent saw last time, so this turn can say what changed; a cursor into your own records; a note that something was already announced.

```json title="newt/turn result"
{
  "instructions": "New since the last turn: task #13, Renew passport.",
  "state": { "last_seen_task": 13 }
}
```

- **`newt/turn` sets it.** newt saves the returned `state` in the same transaction that commits the turn and sends it back on the next one. A turn that does not commit saves nothing, so the state never runs ahead of the session's history. Absent or `null` keeps the previous state; `{}` resets it.
- **Pages and tools patch it.** A `resources/read` result can carry `_meta["newt/state_patch"]`, and a tool result `newt/state_patch`: a JSON merge patch ([RFC 7396](https://www.rfc-editor.org/rfc/rfc7396)) that touches only the keys it names, so a page read and a tool call running at the same time do not overwrite each other.
- **Your servers can read it.** Every resource read and tool call to a server that speaks newt carries `newt/state`, with the turn's patches applied so far.

:::caution
A patch is lost if the turn does not commit, if it arrives after the commit, or if the turn resumes after a crash (replayed results do not patch again). Keep in the state what you can recompute, and keep the record of anything that must not happen twice in your own data.
:::

Keep the state to a few kilobytes. Servers that do not declare the `newt` extension never receive it.

## Hear when a turn ends

Declare `"turn_end": true` and newt sends the home `newt/turn_end` after every committed turn. Use it for bookkeeping that follows the agent: mark messages handled, stop a typing indicator, log the run, bill usage.

```json title="newt/turn_end params"
{
  "agent": "assistant",
  "session": "ana",
  "turn": "0198f2a4-6b1e-7c3d-9a10-5e7d2c8b4f01",
  "outcome": "completed",
  "events": [{ "id": "m1", "meta": { "channel": "whatsapp" } }],
  "state": { "last_seen_task": 13 },
  "turn_state": { "sent": true },
  "reply": "Done: the bank call is on your list for tomorrow at 9."
}
```

`reply` is what the agent said when it finished: the text of the message that called `end_turn`, or of the text-only message just before it. Post it to a chat or a thread from here, and the agent needs no send tool. It is `null` when there is no such text, and always for `failed` and `dead_lettered`.

| `outcome` | When |
|---|---|
| `completed` | The turn ended normally. |
| `failed` | The turn failed after it had effects, and was committed with what it did. |
| `dead_lettered` | newt gave up on the events after `max_attempts` failed turns with no effects. |

`events` lists every event the turn consumed, steered ones included. The request is written in the same transaction as the turn and delivered at least once: right away, then again with backoff for about two hours until you answer with a result instead of an error. Deduplicate by `turn`, and expect requests to arrive late or out of order.

## Rules newt enforces

- `newt/turn` and `newt/turn_end` time out after 10 seconds. newt does not retry inside a request.
- Decoding is strict: unknown fields or an unknown model alias fail the turn loudly.
- A home that cannot be reached, or a declaration newt rejects, stops the turn from starting. The events stay pending and the session retries with backoff (2 s doubling, up to 300 s).
